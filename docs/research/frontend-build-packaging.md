# Research: Frontend Build and Packaging Options for the Decision-Graph Explorer UI

**Context pointer:** https://github.com/McFuzzySquirrel/Engineering-Journey-System/issues/36 ("Research frontend build and packaging options"), scoped to support the read-only UI requested in issue #33, feeding a framework decision tracked separately in issue #35 (explicitly **not** decided here).

All facts below were verified against fetchable primary sources (official docs, changelogs, npm registry, or the tools' own GitHub repos/source) on **2026-10-14**. Where a claim could not be verified from an authoritative primary source, this is stated explicitly rather than guessed.

## Summary

Three build-tool paths are viable: **Vite**, **esbuild** (direct), and **tsup** (esbuild wrapper, already a devDependency) configured as a second, browser-targeted build via an **array-of-configs** in `tsup.config.ts`. All can emit static JS/CSS to a dedicated output directory. Serving those files same-origin from the existing plain `node:http` server requires manual work regardless of build tool, because Node's `http`/`fs` modules have **no built-in static-file server or MIME-type table** — confirmed directly in the current Node.js API docs. A minimal, actively-maintained dependency (`sirv`, last published 2025-09-03, v3.0.2) is the lowest-effort way to add correct `Content-Type`/SPA-fallback/caching semantics without pulling in Express; `serve-static` (Express's own middleware, v2.2.1, last published 2025-12-15) is also current but is designed to be mounted via an Express-style `(req, res, next)` middleware signature and needs a small adapter to drive it from a bare `http.createServer` callback. For npm packaging, the existing `files: ["dist"]` field is sufficient as long as the UI build also writes under `dist/` (e.g. `dist/ui`); `prepublishOnly`/`prepack` are the npm-documented lifecycle hooks to guarantee both builds run before `npm publish`/`npm pack`, and the `exports` field (not currently used in this package.json) only governs `import`/`require` resolution — it has no effect on static assets served via `fs`, which is confirmed by the Node.js/npm docs language describing `exports`/`main` purely in terms of module entry-point resolution. One notable and important finding: **tsup's own GitHub README currently (main branch, checked 2026-10-14) carries an explicit maintenance-status banner** stating "This project is not actively maintained anymore. Please consider using tsdown instead," which is a materially relevant fact for choosing it as a long-term second build target despite its continued presence as the project's existing CLI bundler.

## A. Build tooling options

### Vite
- **Current major / activity:** npm registry `dist-tags.latest` = **8.3.4**, published **2026-10-08T12:07:04Z** (verified via `https://registry.npmjs.org/vite`, queried 2026-10-14). The project's own changelog (`https://raw.githubusercontent.com/vitejs/vite/main/packages/vite/CHANGELOG.md`) shows releases on 2026-10-08 (8.3.4), 2026-10-06 (8.3.3), and 2026-10-01 (8.3.2) — multiple releases within the last two weeks, indicating active maintenance.
- **Architecture note (important, recent):** Vite's own package README (`https://raw.githubusercontent.com/vitejs/vite/main/packages/vite/README.md`) now states: "A build command that bundles your code with **Rolldown**, pre-configured to output highly optimized static assets for production." This is Vite's current (Rolldown-based) production bundler, not classic Rollup — relevant if cross-referencing older tutorials/blog posts (which this report avoids per instructions).
- **Output characteristics**, from `https://vite.dev/guide/build.md` and `https://vite.dev/config/build-options.md`:
  - Default build entry is `<root>/index.html`, producing "an application bundle suitable to be served over a static hosting service."
  - `build.outDir` config option controls output location (default `dist`); `build.assetsDir` nests generated assets under `outDir`; `build.emptyOutDir` defaults to `true` "if `outDir` is inside root," with Vite warning (not erroring) if `outDir` is outside root — directly relevant to not clobbering the existing tsup `dist/` CLI output, since `outDir` can simply be pointed at a sibling directory such as `dist/ui`.
  - Code-splitting is configurable via `build.rolldownOptions.output.codeSplitting` (per Rolldown docs linked from Vite's build guide) — i.e. splitting is handled by the underlying bundler and exposed through Vite's `rolldownOptions` passthrough, confirming Vite does support code-splitting for production builds.
  - Vite supports a documented **Multi-Page App** pattern (`https://vite.dev/guide/build.md`, "Multi-Page App" section) by specifying multiple `.html` entry points, and a documented **Library Mode** (`build.lib`) for non-HTML-entry bundles — giving an official pattern for configuring more than one build purpose from one Vite config if needed later.
  - `https://vite.dev/guide/static-deploy.md` confirms the standard output is the `dist` folder deployed as static files, and that `vite preview` boots a local static server for testing only ("not meant as a production server") — i.e. Vite does not ship its own production static-file server; one is still needed at runtime, which is exactly what this project would wire into its existing `node:http` server.
- **Multiple build targets without clobbering the existing tsup output:** the official, documented mechanism is simply to point Vite's own `build.outDir` at a distinct directory (e.g. `dist/ui`) separate from tsup's `dist/` CLI output — both are independent CLI invocations (`tsup` for the CLI, `vite build` for the UI) with their own config files (`tsup.config.ts`, `vite.config.ts`), so there is no shared state to clobber as long as `outDir`s don't overlap and neither tool's `clean`/`emptyOutDir` behavior targets the other's directory.

### esbuild
- **Current version:** npm registry `dist-tags.latest` = **0.28.2**, published **2026-08-08T20:00:55Z** (verified via `https://registry.npmjs.org/esbuild`, queried 2026-10-14). The GitHub releases feed (`https://github.com/evanw/esbuild/releases`) shows ongoing bug-fix releases addressing tree-shaking, CSS minification, and JS API correctness — consistent with active maintenance, though the exact "latest" version number in that feed could not be isolated from the fetched content beyond confirming recent, substantive activity.
- **Output characteristics**, from `https://esbuild.github.io/getting-started/`: "The bundler outputs code for the browser by default, so no additional configuration is necessary to get started." Supports `--bundle`, `--minify`, `--sourcemap`, `--target=<browserlist>` flags/API options directly. esbuild is lower-level than Vite: it does not generate an `index.html` for you, has no dev server with HMR, and (per tsup's own docs, see below) code-splitting only reliably works for ESM output. Using esbuild directly would mean hand-rolling the `index.html` and asset-hashing strategy.
- Since tsup is "powered by esbuild" (per tsup's own README/docs, `https://raw.githubusercontent.com/egoist/tsup/main/README.md`), using esbuild directly vs. via tsup is mostly a question of whether tsup's conveniences (config-array support, `outExtension`, CSS pass-through) or raw esbuild's smaller API surface is preferred — both ultimately run the same bundler engine.

### tsup (already a devDependency, `^8.5.1` per this repo's `package.json`)
- **⚠️ Maintenance status — important finding.** The current `README.md` on the `egoist/tsup` GitHub repository's `main` branch (fetched 2026-10-14 via `https://raw.githubusercontent.com/egoist/tsup/main/README.md`) opens with:
  > "> [!WARNING]\n> This project is not actively maintained anymore. Please consider using [tsdown](https://github.com/rolldown/tsdown/) instead. Read more in [the migration guide](https://tsdown.dev/guide/migrate-from-tsup)."

  This is a direct, explicit, current statement from the tool's own repository, not an inference. (`tsdown`, the suggested successor, bills itself at `https://tsdown.dev/` as "The Elegant Library Bundler, Powered by Rolldown".)
- **Version data is inconclusive/odd and should not be over-trusted:** the npm registry (`https://registry.npmjs.org/tsup`) lists `dist-tags.latest` = **9.0.0** with a publish timestamp of **2026-10-14T13:47:00Z** — i.e., the same day this research was run, following a roughly 11-month gap after `8.5.1` (published 2025-11-12). Given the explicit deprecation banner in the README at the same moment, this is a notable inconsistency worth flagging rather than resolving with confidence; **treat the "actively maintained" status as negative (deprecated-in-favor-of-tsdown) per the primary README source**, and treat the specific version/date pairing as weakly corroborated.
- **Does it support a browser-targeted second build?** Yes, confirmed directly from source, `https://raw.githubusercontent.com/egoist/tsup/main/src/options.ts`:
  - Line 11: `export type Format = 'cjs' | 'esm' | 'iife'`
  - Line 198: `platform?: 'node' | 'browser' | 'neutral'`
  - i.e. tsup natively supports `format: ['esm','iife']` and `platform: 'browser'` as documented options, confirmed by both source and the docs' "Bundle formats" section (`https://raw.githubusercontent.com/egoist/tsup/main/docs/README.md`, "Supported format: `esm`, `cjs`, (default) and `iife`").
  - CSS: tsup docs state "esbuild has experimental CSS support, and tsup allows you to use PostCSS plugins on top of native CSS support" (same docs file, "CSS support" section) — CSS output is explicitly called **experimental**, which matters for a production UI build.
- **Multiple build targets in one repo without clobbering existing output:** confirmed directly from source, `https://raw.githubusercontent.com/egoist/tsup/main/src/index.ts` line ~177–183:
  ```
  const configData = ...
  [...(Array.isArray(configData) ? configData : [configData])].map(...)
  ```
  This shows tsup's config loader explicitly accepts either a single config object **or an array of config objects** from `tsup.config.ts`. This is the officially-supported mechanism for running two distinct builds (e.g. one `platform: 'node', format: ['esm'], outDir: 'dist'` entry for the CLI, and a second `platform: 'browser', format: ['esm'], outDir: 'dist/ui'` entry for the explorer UI) from a single `tsup` invocation/config file, each with its own `outDir` so neither clobbers the other.
- tsup has no HMR dev server and no official SPA-serving story — it is purely a bundler, same as esbuild.

## B. Static serving from Node `http`

- **Verified: Node's built-in `http`/`fs` modules have no static-file-server or MIME-type-detection utility.** Searching the current official Node.js `fs` API docs (`https://nodejs.org/api/fs.html`, fetched 2026-10-14) for "mime" turns up exactly one unrelated hit: the `type` option on `Blob` construction ("An optional mime type for the blob"). There is no `fs.serveStatic`, no extension→Content-Type table, and no such utility documented anywhere in `https://nodejs.org/api/http.html` either (reviewed the `http.createServer` section, which only documents request/response stream handling — "It deals with stream handling and message parsing only"). This confirms the premise in the research question: a hand-rolled or library-based mapping from file extension to `Content-Type`, combined with `fs.createReadStream`/`fs.promises.readFile` and manual range/caching handling, is still required as of current Node.js docs.
- **Options to fill the gap**, both verified via the npm registry (queried 2026-10-14):
  - **`sirv`** (`https://www.npmjs.com/package/sirv`) — registry description: "The optimized & lightweight middleware for serving requests to static assets." Latest version **3.0.2**, published **2025-09-03T22:05:27Z** (`https://registry.npmjs.org/sirv`). Repository: `lukeed/sirv`. `sirv` is designed to be used directly against Node's raw `(req, res)` handler signature (it is not an Express-only middleware), which fits a bare `http.createServer` callback with minimal glue — a good match for the existing `routeRequest(request, response, store, config)` style already used in `src/server/http.ts`. It supports an `fallback` option for SPA-style single-page routing commonly needed for client-side-routed UIs (this specific option name should be re-verified against sirv's own README at implementation time, since this report avoided non-primary tutorial sources describing it in detail).
  - **`serve-static`** (`https://www.npmjs.com/package/serve-static`) — registry description: "Serve static files." Latest version **2.2.1**, published **2025-12-15T19:17:31Z**; a **1.16.3** maintenance release was also published the same day (`https://registry.npmjs.org/serve-static`), suggesting the maintainers (Express/`expressjs` org — `repository: expressjs/serve-static`) are actively back-porting fixes to the 1.x line while shipping 2.x. `serve-static` is built around Express's `(req, res, next)` middleware convention; using it from a bare `node:http` server (no Express) requires manually invoking it as `serveStatic(dir)(req, res, next)` and supplying a `next` callback for the "not found, fall through" case — it is not designed for drop-in zero-glue use outside an Express-compatible middleware chain.
  - Both are current/maintained by the dates above; `sirv` is the lower-friction choice for a non-Express `http.createServer` the project already has (less adapter code), `serve-static` is a reasonable choice only if an Express-like middleware chain is adopted later.
- Regardless of library choice, **SPA fallback (serving `index.html` for unknown non-API GET paths so client-side routing works) is an application-level routing decision**, not something Node or these libraries do automatically for arbitrary paths; it needs to be wired explicitly in `routeRequest` (e.g., "if path doesn't match a known API route and isn't a static asset that exists, serve `index.html`") — this is consistent with how the existing file already dispatches routes by `url.pathname` (see `src/server/http.ts:100-132`, `routeRequest`), so the fallback is just one more branch in that same function, ordered after the existing `/projects`, `/search`, `/context`, `/mcp`, and push routes, and after attempting a static-file lookup.

## C. npm packaging implications

All claims in this section are drawn from `https://docs.npmjs.com/cli/v10/configuring-npm/package-json` (`#files`, `#exports`, `#main`) and `https://docs.npmjs.com/cli/v10/using-npm/scripts`, fetched 2026-10-14.

- **`files` field semantics** (docs, `#files` section, verbatim): "The optional `files` field is an array of file patterns that describes the entries to be included when your package is installed as a dependency... Omitting the field will make it default to `["*"]`... You can also provide a `.npmignore` file... At the root of your package it will not override the `files` field, but in subdirectories it will." Practically: the existing `"files": ["dist"]` entry in this repo's `package.json` already covers **any** contents under `dist/`, including a new `dist/ui/` subdirectory, as long as the UI build writes there — no `package.json` change to `files` is needed if the UI build output lands inside `dist/`. A root-level `.npmignore`, if one existed, could not override `files` at the root (per the quoted text), so there is no risk of an existing ignore file silently excluding the new subdirectory at the root level; subdirectory-level `.npmignore` files, if added inside `dist/ui`, could still exclude content there and should be avoided/checked.
- **Running two build steps before publish:** npm's own lifecycle docs (`#using-npm-scripts`) describe `prepublishOnly` and `prepack` as documented lifecycle events: "`prepublishOnly`" is listed as a dedicated life-cycle script alongside `prepare`/`prepack`/`postpack`, and the "Life Cycle Operation Order" section explicitly lists `npm pack` and `npm publish` as events that run these scripts. The doc's own guidance under "Prepare and Prepublish" states the general use case: "If you need to perform operations on your package before it is used... use a `prepublish` script [family]... This includes tasks such as [build steps]." This directly supports using `"prepublishOnly": "npm run build && npm run build:ui"` (or a single script that runs both the existing `tsup` CLI build and the new UI build) as the current, npm-documented way to guarantee both outputs exist before `npm publish`; `prepack` is the equivalent hook that also covers `npm pack` (useful for local tarball testing without actually publishing).
- **`exports` field and static assets:** the npm docs describe `exports` purely as a module-resolution mechanism: "The 'exports' provides a modern alternative to 'main' allowing multiple entry points to be defined, conditional entry resolution support between environments, and **preventing any other entry points besides those defined in 'exports'**." This governs what `import`/`require` can resolve to when *other Node packages* import this package as a module — it has no bearing on files served via `fs.createReadStream`/`fs.readFile` at runtime by the `dg serve` HTTP server, since that is plain filesystem access, not a module resolution operation. This repo's `package.json` does not currently define an `exports` field at all (confirmed by viewing the file directly), so this is a non-issue either way, but worth noting for completeness per the research question: **verified — `exports` does not affect static asset serving.**

## D. tsup dual-target feasibility (detailed)

Already substantiated with source citations in section A, summarized as a direct answer:

- **Yes, tsup can do double duty** as both the Node-targeted CLI bundler and a browser-targeted UI bundler, via an array of config objects in one `tsup.config.ts` (`egoist/tsup:src/index.ts` config-array handling, confirmed above) with per-entry `platform: 'node' | 'browser'`, `format`, and distinct `outDir` (`egoist/tsup:src/options.ts:130,195-198`).
- **But:** tsup's own README currently flags the project as not actively maintained, pointing at `tsdown` as the suggested replacement (`egoist/tsup README.md`, fetched 2026-10-14). Building a net-new UI pipeline on top of a tool whose own maintainers say "not actively maintained" is a real tradeoff against the "currently supported, actively maintained" requirement in part A of the research question, even though it is already a devDependency and avoids adding a new one.
- **tsup vs. esbuild directly:** since tsup is "powered by esbuild" per its own docs, choosing raw esbuild instead of tsup for the browser build avoids depending on tsup's config/array behavior at all, at the cost of hand-writing `index.html` generation/asset copying and whatever CSS handling is needed (esbuild's CSS support is also still experimental per its own content-types docs, linked from tsup's docs).
- **tsup/esbuild vs. Vite:** Vite adds HMR dev server, documented `outDir`/`assetsDir`/`emptyOutDir` config for avoiding clobbering, a documented static-deploy story, and (via its underlying Rolldown bundler) code-splitting — but it is a new devDependency with its own config file (`vite.config.ts`) distinct from `tsup.config.ts`, and it is the heaviest of the three options in terms of dependency surface and concept count (plugins, dev server, SSR features not needed here).

## Recommendation

For a **read-only, framework-undecided (issue #35), lightweight explorer UI** that must same-origin-serve from the existing `node:http` server and ship inside the existing `dist/` npm `files` entry:

| Approach | Dev experience | Output/asset hashing | Config complexity | New deps | Maintenance signal |
|---|---|---|---|---|---|
| **Vite** (new devDependency) | Best: instant dev server + HMR; `vite preview` for local static smoke-test | Rolldown-backed hashed assets, code-splitting, official `outDir`/`assetsDir` controls | One new config file (`vite.config.ts`), but conventions are well-documented | +1 (vite) | Actively maintained, frequent releases (verified 2026-10-01/06/08 release cadence) |
| **tsup second config entry** (no new devDependency) | Manual rebuild-and-refresh, no HMR | Hashing/splitting not confirmed; CSS support explicitly "experimental" | Low — reuses existing `tsup.config.ts` as an array | +0 | Negative — upstream README says "not actively maintained," recommends `tsdown` |
| **esbuild directly** (new devDependency, or reuse via tsup's own esbuild dep) | Manual, no HMR; need to hand-build `index.html`/asset copy | Minimal/manual; esbuild bundles for browser by default but doesn't scaffold HTML/hashing for you | Low API surface but more hand-rolled glue code | +0 or +1 depending on whether used via tsup or standalone | Actively maintained per recent GitHub releases (exact latest tag not confirmed beyond registry's 0.28.2 / 2026-08-08) |

**Suggested direction:** Use **Vite** for the UI build, writing to a distinct `build.outDir` (e.g. `dist/ui`) so it never collides with the existing `tsup`-produced `dist/cli.js` and other CLI output, and add `"prepublishOnly": "npm run build && npm run build:ui"` (two scripts) so both builds are guaranteed to run before `npm publish`/`npm pack`. Serve `dist/ui` same-origin from the existing `routeRequest` function in `src/server/http.ts` by adding a static-file branch (ideally via `sirv`, given it fits the bare-`http.createServer` handler shape already in use, versus `serve-static`'s Express-middleware-first design) with an SPA fallback to `index.html` for unmatched non-API GET paths, placed after the existing `/projects`, `/search`, `/context`, `/mcp`, and push routes. This satisfies "actively maintained build tool," "same-origin static serving from the existing plain `http` server," and "packaged via the existing `files: ["dist"]`" without requiring Express. The main tradeoff accepted is one new devDependency (Vite) and its config file, versus zero new dependencies but betting on a tool (tsup) whose own maintainers currently recommend migrating away from it.

If the team instead prefers **zero new devDependencies**, the tsup-array-of-configs approach is mechanically sound (confirmed from tsup's own source) and defensible as a stop-gap, but should be revisited once issue #35 picks a concrete framework, since tsup's own README is actively steering users toward `tsdown` and CSS handling in both tsup and raw esbuild is still labeled experimental by their own docs.

## Facts vs. open decisions

**Verified facts (with citations above):**
- Node's `fs`/`http` docs confirm no built-in MIME-type table or static file server (`nodejs.org/api/fs.html`, `nodejs.org/api/http.html`, checked 2026-10-14).
- `sirv` latest is 3.0.2, published 2025-09-03 (npm registry); `serve-static` latest is 2.2.1, published 2025-12-15, with a 1.16.3 release the same day (npm registry).
- Vite latest is 8.3.4, published 2026-10-08, with releases on 2026-10-01/06/08 (npm registry + Vite's own CHANGELOG.md) — Vite's production builder is now Rolldown-based per Vite's own README.
- esbuild latest is 0.28.2, published 2026-08-08 (npm registry); GitHub releases show ongoing bug-fix activity.
- tsup's own repository README (main branch, 2026-10-14) explicitly states it is "not actively maintained anymore" and recommends `tsdown`; tsup npm registry nonetheless shows a 9.0.0 release dated the same day as this research, an inconsistency flagged rather than resolved.
- tsup supports `platform: 'node'|'browser'|'neutral'` and `format: 'cjs'|'esm'|'iife'` as config options (tsup source, `src/options.ts`), and its config loader accepts an array of config objects for multiple simultaneous build targets (tsup source, `src/index.ts`).
- npm's `files` field includes everything under a listed directory (e.g. `dist`) unless overridden by a subdirectory `.npmignore` (root-level `.npmignore` cannot override `files`) — per `docs.npmjs.com` package.json docs.
- `prepublishOnly`/`prepack` are npm-documented lifecycle hooks that run before `npm publish`/`npm pack` respectively — per `docs.npmjs.com` scripts docs.
- The `exports` field governs module resolution only and has no bearing on filesystem-served static assets — per `docs.npmjs.com` package.json docs language, and confirmed this repo's `package.json` does not currently define `exports` at all.

**Open decisions deferred to other tickets (not decided here):**
- The actual UI framework (vanilla/Preact/lit/React) — explicitly issue #35.
- Whether to adopt Vite vs. tsup-array vs. raw esbuild — a recommendation is offered above, but the final call, and any related dependency-budget tradeoff discussion, is a decision for the team/issue #36 follow-up, not something this research report finalizes.
- The exact SPA-fallback and static-serving library (`sirv` vs. a hand-rolled minimal implementation vs. `serve-static` with an adapter) — recommended direction given, but not implemented/verified against this repo's actual `routeRequest` code path in this research pass.
- Whether tsup's "not actively maintained" status is disqualifying enough to also migrate the *existing* CLI build to `tsdown` — out of scope for issue #36, which only concerns the new UI build target.
