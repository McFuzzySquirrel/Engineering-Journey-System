# Sub-Agent Contributions

## Sub-Agent: explore agent (game architecture design)
- **Task delegated:** Design the architecture for a 3D Asteroids game using Babylon.js. Recommend file structure, Babylon.js loading approach, game mechanics, 3D models, camera type, physics approach, and overall code organization.
- **Decisions made:**
  1. **Single HTML file** over multi-file structure — chose zero-build-tool simplicity for a self-contained demo
  2. **CDN loading** (Babylon.js v5.0 suggested, though implementation used latest) — no bundler needed
  3. **Procedural meshes** (cone for ship, icosphere for asteroids) over imported 3D models — eliminates asset pipeline
  4. **No physics engine** (manual bounding-sphere collision) over Cannon.js integration — simpler for this scope
  5. **Chase camera** (FollowCamera) over first-person or fixed — better spatial awareness for 3D asteroids
  6. **Simple object pattern** for game state over class hierarchy — lower overhead, easier to serialize
- **Alternatives considered:**
  - Multi-file structure with separate JS modules (rejected: adds build complexity)
  - Imported 3D models via .glb/.gltf (rejected: requires asset pipeline and hosting)
  - Cannon.js physics engine (rejected: overkill for bounding-sphere collisions)
  - First-person camera (rejected: poor spatial awareness for asteroid dodging)
  - Fixed overhead camera (rejected: less immersive for 3D game)
- **Outcome:** Complete architecture specification with file structure, code layout, controls mapping, and implementation details table
- **Handoff to other agents:** Full architecture specification passed directly to general-purpose agent as implementation context — the decisions about single-file, procedural meshes, chase camera, and manual collisions shaped the entire implementation

## Sub-Agent: general-purpose agent (game implementation)
- **Task delegated:** Implement a complete, playable 3D Asteroids game in a single HTML file using Babylon.js, following the architecture decisions from the explore agent. Specific requirements: WASD/arrow controls, asteroids that split, collision detection, HUD, wave system, particle effects, game over/restart.
- **Decisions made:**
  1. **TransformNode-based ship** with child meshes (body cone, wings, cockpit, engine glow) over single-mesh approach — allows individual part styling and future animation
  2. **SolidParticleSystem (SPS)** for starfield (1200 particles) over individual sphere meshes — vastly better performance
  3. **Vertex deformation** on icospheres for asteroid irregularity over uniform spheres — more visually authentic
  4. **AdvancedDynamicTexture GUI** for HUD over HTML overlay — stays in Babylon.js ecosystem, renders in WebGL
  5. **Delta-time-based game loop** (`engine.getDeltaTime()`) over fixed-step — smooth on any framerate
  6. **Ship invulnerability flicker** (180 frames) on respawn over instant vulnerability — standard arcade game UX
  7. **Bullet velocity inherits 30% of ship velocity** over pure directional fire — feels more natural in motion
- **Alternatives considered:**
  - Single mesh for ship (rejected: couldn't style cockpit/engine separately)
  - Individual sphere meshes for stars (rejected: 1200 draw calls would tank performance)
  - HTML div overlay for HUD (rejected: would require managing two rendering systems)
  - Fixed time-step physics (rejected: unnecessary complexity for arcade game)
- **Outcome:** Complete 715-line game/index.html — fully playable with all requested features, visual polish (particles, glow materials, fog), and arcade-style UX
- **Handoff to other agents:** Completed game file handed off to task agent for server setup and validation; also used directly by main agent for browser testing

## Sub-Agent: task agent (build validation and server setup)
- **Task delegated:** Start an HTTP server for the game directory, verify the server serves the file correctly, and confirm Babylon.js CDN scripts are referenced properly in the HTML output.
- **Decisions made:**
  1. **Python http.server** over Node.js http-server — already available, no install needed
  2. **curl-based verification** over browser-based — faster for initial smoke test
  3. **Checked script tags and HTML structure** rather than just HTTP status — validates functional correctness not just serving
- **Alternatives considered:**
  - Node.js http-server or live-server (rejected: would need npm install, Python is built-in)
  - Only check HTTP 200 status (rejected: doesn't verify the actual content is correct)
- **Outcome:** Server confirmed running, HTML structure valid, Babylon.js CDN scripts correctly referenced. Identified that the game would load dependencies correctly.
- **Handoff to other agents:** Validation results confirmed to main agent that the game file was structurally sound. However, main agent discovered CDN was blocked in sandbox during browser testing — this triggered the pivot to local npm-installed files (a decision the task agent couldn't have anticipated since it only checked HTML references, not actual CDN connectivity)

# Experiments / Evidence

**What was tried?**
1. Loading Babylon.js from CDN (cdn.babylonjs.com) in the browser
2. Downloading babylon.js via curl directly
3. Installing babylonjs via npm and copying local files

**What happened?**

**What evidence changed your mind?**

- npm's successful install proved the package was available through a different channel
- After switching to local files, `Babylon.js v8.50.2 - WebGL2` appeared in console — game fully functional

# Decisions Made

- **Decision:** Use single-file architecture (game/index.html) with Babylon.js
  - **Reason:** Zero build complexity, self-contained demo, recommended by explore agent
  - **Impact:** Entire game in one file — easy to deploy, review, and understand

- **Decision:** Use procedural meshes instead of imported 3D models
  - **Reason:** Eliminates asset pipeline, explore agent weighed this against .glb imports
  - **Impact:** Ship built from cones/boxes/spheres, asteroids from deformed icospheres — no external assets needed

- **Decision:** Pivot from CDN to local npm-installed Babylon.js files
  - **Reason:** CDN blocked in sandbox environment (discovered during browser testing)
  - **Impact:** Added .gitignore entries for local .js files, game works offline

- **Decision:** Use 4 distinct sub-agents for different phases (explore, general-purpose, task, plus main orchestrator)
  - **Reason:** Tests the Sub-Agent Decision Capture Protocol (ADR 0012) with real multi-agent collaboration
  - **Impact:** Each agent's decisions captured in Sub-Agent Contributions section — protocol validated

# Key Learnings

**Technical insights:**
- Babylon.js SolidParticleSystem is the right choice for starfields (1200 particles with frozen world matrix = no performance cost)
- Vertex deformation on icospheres creates convincing asteroid shapes with minimal code
- FollowCamera with tuned acceleration/offset provides good chase-cam feel out of the box
- npm registry may be accessible even when CDN domains are not in sandboxed environments

**Prompting insights:**
- Providing the explore agent's architecture decisions as explicit context to the general-purpose agent produced a coherent implementation that matched the design
- Asking sub-agents to recommend approaches (not just implement) generates richer decision data for the Sub-Agent Contributions section
- The handoff chain (explore → general-purpose → task) naturally produces the inter-agent collaboration data the protocol was designed to capture

**Tooling insights:**
- Python's http.server is sufficient for validating static HTML games — no need for Node.js tooling
- Local copies of CDN libraries should be .gitignored with a comment pointing to the CDN URLs for production use
- npm pack tgz files can accidentally get committed — add *.tgz to .gitignore proactively

# If Repeating This Work

**Do this:**
- Start with an architecture sub-agent before implementing — the design decisions flow naturally into implementation context
- Use local copies of CDN libraries from the start in sandboxed environments
- Add *.tgz to .gitignore before running any npm commands
- Keep the game in a single file for simplicity — multi-file adds build complexity without proportional benefit for a demo

**Avoid this:**
- Don't assume CDN access in sandboxed environments
- Don't skip the .gitignore setup before running npm

**Watch out for:**
- npm pack tgz files appearing in the repo root (not in node_modules)
- Babylon.js version mismatches between CDN references and npm-installed files
- SPS starfield must have frozen world matrix to avoid performance issues

# Future Agent Guidance

**Prefer:**
- Delegating distinct phases (design, implement, validate) to different sub-agents
- Passing prior sub-agent output as explicit context in delegation prompts
- Using explore agent for architecture decisions (it produces structured, decision-rich output)
- Using general-purpose agent for complex implementation (it handles large code generation well)
- Using task agent for build/validation (it's efficient for command execution)

**Avoid:**
- Having a single agent do everything (misses the multi-agent collaboration capture)
- Delegating without providing prior sub-agent decisions as context (breaks the handoff chain)
- Assuming external network access (CDN, APIs) in sandboxed environments
