# Experiments / Evidence
What was tried? Measured actual byte sizes of 14 journey files (2.7KB–18.8KB). Compared equivalent content in markdown vs JSON encoding (110 chars vs 155 chars for a single field — 41% larger in JSON). Read all of adr-db.py to confirm the journeys table schema and query commands already exist.
What happened? Every line of evidence pointed away from format change and toward DB-first enforcement as the efficiency lever.
What evidence changed your mind? Discovering that `summary-journeys`, `get-journey`, `search`, and `list-journeys` commands are all already implemented and working — this made the "we need JSON for machine querying" premise collapse. The machine querying layer already exists.

# Decisions Made
- Decision: Recommend against JSON journey files.
  - Reason: JSON adds encoding overhead (typically 20–50% larger for narrative text), breaks human-readability, increases agent failure risk (invalid JSON = silently dropped during DB sync), and does not change what the DB returns to agents.
  - Impact: Research finding only. No code changes. Closes the hypothesis with evidence.
- Decision: Recommend adding a `story` command to `adr-db.py`.
  - Reason: Current `summary-journeys` truncates at 300 chars which is insufficient for understanding a session. A richer narrative summary would make DB-first genuinely preferable to raw file reads.
  - Impact: Small enhancement to adr-db.py. Makes DB-first adoption easier.

# Key Learnings
Technical insights: JSON is not inherently compact for text content. The SQLite DB is the correct abstraction for context efficiency — what matters is that agents always query it and it is always synced.
Prompting insights: "Question everything" is the right instinct. The hypothesis assumed a logical chain that broke under scrutiny.
Tooling insights: `adr-db.py` already has all the query commands needed for DB-first operation. The gap is behavioral enforcement (hooks guarantee sync, instructions mandate DB query), not tooling.

# If Repeating This Work
Do this: Measure actual file sizes and content encoding costs before proposing format migrations. Check whether existing tooling already solves the problem.
Avoid this: Don't assume that "machine-friendly format" equals "less context." The DB abstraction layer is the context saver — the format below it is irrelevant.
Watch out for: Format migration proposals that promise efficiency gains. They rarely deliver because the efficiency problem is usually in how the data is accessed (DB vs raw read), not in how it is stored.

# Future Agent Guidance

Avoid: Reading raw journey markdown files when a DB query will answer the question. Proposing format changes without first measuring whether the format is the actual bottleneck.
