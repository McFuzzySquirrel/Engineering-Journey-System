# Problem / Intent
Reframe the EJS agent from an implementation assistant to a **non-competing observer/recorder** that can be bootstrapped into repos with existing agents. The agent was incorrectly positioned as doing implementation work ("assist with implementation", "propose solutions") when its actual purpose is to capture what *other* agents and humans are doing.

Proposed reframing as a non-competing observer. Identified that copilot-instructions.md is the only always-on injection point, while the agent profile requires manual selection.

# Decisions Made
- Decision: Reframe EJS agent from implementation assistant to non-competing observer/recorder
  - Reason: EJS is designed to be bootstrapped into repos with existing agents — it must not compete with or duplicate their work
  - Alternatives: (A) Keep as implementation agent that also records, (B) Pure observer with no agent profile, (C) Observer with three adoption tiers
  - Impact: All four core files rewritten — agent profile, copilot-instructions.md, journey template, README

- Decision: Three-tier adoption model (always-on, bookend, coordinator)
  - Reason: Platform limitation prevents background agent persistence; three tiers give maximum flexibility
  - Alternatives: (A) Always-on only, (B) Always-on + explicit invocation, (C) Three tiers including coordinator
  - Impact: Agent profile restructured around tiers; README adoption kit updated with tier table

- Decision: Silent automatic recording (no prompting)
  - Reason: The observer must never interrupt the implementation workflow — recording is a side-effect, not a conversation
  - Alternatives: (A) Prompt for capture when decisions detected, (B) Silent automatic recording
  - Impact: copilot-instructions.md explicitly forbids prompting; recording happens automatically

- Decision: Appendable copilot-instructions.md (not replacement)
  - Reason: Target repos already have copilot-instructions.md with their own agent instructions — EJS must layer on top
  - Alternatives: (A) Replace existing file, (B) Separate file, (C) Appendable block
  - Impact: copilot-instructions.md redesigned with clear "append this block" framing and self-contained contract

# Key Learnings
- GitHub Copilot custom agents cannot run in background or persist across agent switches — they are session-scoped to their selection
- copilot-instructions.md is the only truly always-on mechanism — it applies to every Copilot interaction regardless of agent selection
- The `tools: ['agent']` and `agents: ['*']` frontmatter fields enable coordinator mode delegation
- Designing for "bootstrap into existing repos" requires fundamentally different thinking than "standalone agent"

# If Repeating This Work
Do this: Start with the platform constraints research first — understanding what is/isn't possible shapes the entire design
Avoid this: Assuming agents can run concurrently or in background — the platform doesn't support it
Watch out for: The journey template and copilot-instructions.md need to stay in sync on attribution format (`Agent [name]:`)

# Future Agent Guidance
Prefer: Three-tier model when designing observability tools — give users flexibility without requiring specific agent selection
Avoid: Claiming implementation capability for observer/recorder agents — it creates confusion about the agent's role
